# Plan: Diagnose the flaky 3.12 Qt segfault in CI (ci-qt-flake-312)

## Context

CI intermittently segfaults on the **Python 3.12** job. This is an investigation plan. Its
job is to produce a measured answer, not to ship a guess.

### The failure

```text
job: test (3.12) -> failure, exit 139
Fatal Python error: Segmentation fault

tests/test___init__.py .                                                 [  0%]
tests/test_actions.py .....                                              [  2%]
Fatal Python error: Segmentation fault
```

It aborts at ~2%, immediately after `tests/test_actions.py`, which constructs `MainWindow`
and Qt actions. `lint` and `test (3.14)` pass.

### Established facts — do not re-derive these

| Measurement | Result |
|---|---|
| CI, 3.12 | **1 crash in 2 runs** (same commit `d5423e4`: one failed, a re-run passed) |
| CI, 3.14 | 0 crashes in 2 runs |
| Local, 3.14 + coverage | 0 crashes in 91 runs |
| Local, 3.12 + coverage | 0 crashes in 10 runs |
| Local, 3.12 + coverage, pinned to 2 CPUs via `taskset -c 0,1` | 0 crashes in 6 runs |

**The crash is flaky in CI and has not been reproduced locally at all.** One crash in two
CI runs bounds the rate very loosely — anywhere from roughly 10% to 50%. Establishing the
real CI rate is Task 2 and everything else depends on it.

This machine has 4 cores; GitHub's `ubuntu-latest` runners have fewer and a different Qt
library set (`libegl1 libgl1 libxkbcommon-x11-0 libdbus-1-3` installed via apt, offscreen
platform).

### A prior fix that is only partly correct

`a913e04` set `[tool.coverage.run] timid = true`, which took the suite from ~7-20% crashing
to 0 in 91 local runs on 3.14. That was real and it should stay.

But its commit message states the root cause as coverage's C tracer corrupting frame state
**under Python 3.14** — and 3.14 is now the leg that passes while 3.12 crashes. **That
explanation is at best incomplete and possibly wrong.** Treat it as a hypothesis, not
settled fact. If this investigation establishes a better explanation, correcting that
record is part of the work (Task 7).

Do **not** remove `timid = true`. It demonstrably helped. Removing it is not a fix.

### What "done" means

A measured answer. Any of these is an acceptable outcome:

1. root cause found and fixed, with a measured before/after CI rate;
2. root cause found but only mitigated, stated plainly as a mitigation;
3. **an honest dead end** — hypotheses tried, each with its measured rate, and a clear
   statement that the cause is not yet known.

What is **not** acceptable: disabling coverage, deleting/skipping/xfailing tests, dropping
the 3.12 matrix leg, or declaring victory on an under-powered sample. This bug has already
defeated three confident fixes in this project (two of mine, one partial); the discipline
below exists because of that.

### Measurement discipline — read this before measuring anything

- **State the decision rule before you run the measurement**, so a marginal result cannot
  be rationalised afterwards.
- **A small clean sample is not evidence.** At a 20% rate, 0 crashes in 15 runs happens
  ~3.5% of the time by chance. Earlier in this project a 0/15 result was reported as a
  confirmed fix and was wrong twice over.
- **Verify a mutation or config change actually applied** before trusting a result. Several
  earlier "no effect" findings were edits that silently did not land.
- **Parse pytest output with `--color=no`.** ANSI codes have already caused `FAILED` lines
  to be missed.
- **Distinguish a native crash from an ordinary test failure.** Exit 139/134, or
  `Fatal Python error` / `Segmentation fault` in the output, is a crash. A normal failing
  assertion is a different problem and must not be counted as flake.

### Constraints

- Do not modify the Streamlit path: `src/wherewolf/app.py`, `engines.py`, `ui/`, `export/`,
  `storage/`, `constants.py`, `.streamlit/`.
- Do not change `timid = true`.
- Do not weaken, skip or delete tests.
- Do not touch `main`. Do not tag or release.
- Prefer configuration or test-lifecycle fixes over production code changes.
- CI minutes are a real cost. The probe workflow in Task 2 is capped deliberately; do not
  raise the cap without saying why in the session log.

### Repo mechanics

- `.git/hooks/pre-commit` runs `ruff check .`, `ruff format .`, `ty check .`, `pytest`,
  then `scripts/check_tdd.sh`. The pytest step runs under coverage.
- `scripts/check_flake.sh N` runs the suite N times locally and fails on any native crash.
- `./run.sh` pins `UV_PROJECT_ENVIRONMENT`, so a 3.12 run must use a separate environment
  directory — see Task 1 for the exact invocation.
- Baseline on `dev` at `d5423e4`: **224 passed, 1 skipped** on both 3.12 and 3.14 locally;
  CI green on the most recent attempt.

c=0
for i in $(seq 1 20); do
  env UV_PROJECT_ENVIRONMENT=/tmp/wherewolf/.venv312 \

### Task 2 — Establish the real CI rate with a parallel probe workflow

One crash in two runs is not a rate. Get a real one.

Add `.github/workflows/flake-probe.yml`:

- trigger: **`workflow_dispatch` only** — it must never run on push or pull_request;
- a matrix of **10** parallel jobs, each running the suite **once** on Python 3.12;
- `fail-fast: false`, so one crash does not cancel the other samples;
- identical setup to the `test` job in `ci.yml`: same apt Qt libraries, same
  `actions/setup-java@v4` Temurin 21, same `uv sync --all-extras --dev --python 3.12`, same
  `./run.sh uv run --python 3.12 pytest`;
- each job must make a native crash unambiguous in its conclusion — a segfault already
  exits 139, so no extra handling is needed, but do not add `continue-on-error`.

Ten parallel jobs give ten independent samples in roughly the time of one run.

Run it and count:

```bash
gh workflow run flake-probe.yml --ref feat/ci-qt-flake-312
# wait for completion, then:
gh run list --workflow flake-probe.yml --limit 1
gh run view <id> --json jobs --jq '[.jobs[] | select(.name|startswith("probe"))] | "crashed: \([.[]|select(.conclusion=="failure")]|length) / \(length)"'
```

**Record the fraction. This is the number every later measurement is compared against.**

Then confirm the crash signature matches the original — pull the log of one failed job and
check it is a segfault after the widget tests, not some unrelated failure:

```bash
gh run view <id> --log-failed | grep -E "Fatal Python error|Segmentation fault|^tests/" | head -20
```

**If 0/10 crash**, the failure is rarer than the single observation suggested. Say so, run
the probe **once more** for 20 total samples, and if still 0/20 stop and report — chasing a
sub-5% CI-only crash is not a good use of further CI minutes, and that is a legitimate
conclusion.

Commit: `ci: add manual flake probe workflow for the 3.12 segfault`.

### Task 3 — Only if Task 1 found a local reproduction: bisect locally

Local iteration is vastly cheaper than CI. If Task 1 crashed even once, work here.

Measure 30 runs per arm, one variable at a time:

1. 3.12 + coverage (the baseline rate);
2. 3.12 + `--no-cov` — does coverage still matter on 3.12?
3. 3.12 + coverage with `timid = false` — how much is `timid` actually buying on 3.12?
4. only the widget test files (`tests/test_actions.py tests/test_main_window.py
   tests/test_catalog_dock.py tests/test_sql_editor.py`) versus the full suite — is it a
   single file or an interaction?

Record all four rates. Commit: `docs: record local 3.12 flake bisection`.

### Task 4 — Narrow the trigger using the probe

Whether or not you have a local repro, narrow **what in the run** triggers it. One variable
per probe dispatch, comparing against Task 2's rate:

1. `-p no:randomly` if any ordering plugin is active, to rule out test-order dependence
   (check whether one is installed before assuming);
2. `--no-cov` on the probe — if the CI rate drops to zero, coverage is still implicated on
   3.12 despite `timid`;
3. deselecting the widget-heavy files, to see whether the crash follows them.

**Do not change more than one variable per dispatch.** Record each rate in the session log
next to Task 2's baseline.

Commit: `docs: record ci flake probe results`.

---

### Task 5 — Test candidate fixes, one at a time

Only now propose fixes, and only ones the evidence supports. Likely candidates, in the
order the evidence would justify:

1. a session-scoped `qapp` fixture with explicit event-loop draining
   (`QApplication.processEvents()` plus `deleteLater` flush) between tests;
2. explicit teardown of `MainWindow`/widget trees rather than relying on Python GC;
3. `concurrency`/`sigterm` coverage options **specifically on 3.12** — note that
   `concurrency=["thread"]` measured 3/40 on 3.14 previously and was reverted, but that
   was a different interpreter;
4. pinning a different coverage or PyQt6 version on 3.12 only, if version-specific evidence
   emerges.

**State the decision rule before each measurement.** With a Task 2 baseline rate of `p`,
decide in advance how many probe samples constitute a pass; for a ~20% baseline, 0/20 is
reasonable (0.8^20 ≈ 1.2%), 0/10 is not.

Stop at the first candidate that reaches your stated threshold. Record the ones that did
not work.

Commit: `fix(ci): <specific change>` for whichever worked.

## Verification

This is an investigation, so verification is mostly about **whether the conclusions are
supported by the measurements** rather than whether a feature works.

### V1 — Nothing was weakened to make the symptom disappear

```bash
grep -n "addopts\|timid\|omit\|concurrency" pyproject.toml
git diff dev..HEAD -- tests/ | grep -E "^\-.*def test_|^\+.*@pytest.mark.(skip|xfail)" || echo "OK: no tests deleted or newly skipped"
git diff dev..HEAD -- .github/workflows/ci.yml
```

**Expected:** `addopts` still contains `--cov=src --cov-report=term`; `timid = true` still
present; no test deleted, skipped or xfailed; and if `ci.yml` changed at all, the
`["3.12", "3.14"]` matrix is **still intact**.

**Failure looks like:** coverage disabled, `timid` removed, tests skipped, or the 3.12 leg
dropped from the matrix. Any of those is making the measurement stop rather than fixing the
bug.

### V2 — The probe workflow cannot fire by itself

```bash
sed -n '1,15p' .github/workflows/flake-probe.yml 2>/dev/null || echo "(probe deleted — acceptable)"
```

**Expected:** if present, the `on:` block contains **only** `workflow_dispatch` — no
`push`, no `pull_request`, no `schedule`.

**Failure looks like:** any automatic trigger. That would burn CI minutes on every push.

### V3 — Local suite still passes on both interpreters

```bash
set -o pipefail
./run.sh uv run pytest -q 2>&1 | tail -2
env UV_PROJECT_ENVIRONMENT=/tmp/wherewolf/.venv312 XDG_CACHE_HOME=/tmp/wherewolf/.cache \
    PYTHONPYCACHEPREFIX=/tmp/wherewolf/__pycache__ TMPDIR=/tmp/wherewolf \
    uv run --python 3.12 pytest -q 2>&1 | tail -2
```

**Expected:** `224 passed, 1 skipped` on both, or higher if tests were added. **Failure
looks like:** any failure, or a lower count.

Then `scripts/check_flake.sh 25` — **expected `0 native crashes in 25 runs`**, confirming
no local regression was introduced.

### V4 — Every claimed rate has its sample size, and the arithmetic holds

Read the session log and check each measurement records **both** numerator and denominator
("2 / 30", never "no crashes"). For the accepted fix, confirm the sample size actually
supports the claim against the Task 2 baseline rate `p`:

```text
false-pass probability ≈ (1 - p)^N
```

**Failure looks like:** a fix accepted on a sample too small to distinguish it from luck —
for example 0/10 against a 20% baseline, which is a 10.7% false-pass. If the log claims a
fix on that basis, the conclusion is not supported and the round is not done.

This step exists because exactly that error was made three times earlier in this project.

### V5 — Real CI, on the merge target

The probe is a proxy. Confirm the actual `ci.yml` workflow passes on the branch:

```bash
gh run list --branch feat/ci-qt-flake-312 --limit 3
```

**Expected:** the most recent `CI` run is green on `lint`, `test (3.12)` and `test (3.14)`.

**Failure looks like:** any red job, or no run at all (the branch was never pushed, so CI
never exercised the change).

Note honestly: a single green CI run does **not** prove a flaky crash is fixed. Report it
as one sample alongside the probe's rate, not as proof.

### Deferred and explicitly NOT verified

- **A single green CI run is not proof.** State the probe rate as the evidence and the CI
  run as corroboration.
- **The crash was never reproduced locally** (unless Task 1 changed that) — so any fix is
  validated only through CI, on GitHub's runner image, at one point in time.
- **macOS and Windows are not tested at all** by this or any current workflow.
- **A residual rate below roughly 1/N** for whatever N the probe used would not have been
  detected. Give the number.
- **If the outcome is a dead end, say so.** An unexplained flake that is documented and
  bounded is a better result than a fix that is asserted without evidence.
